# CONTRIBUTING

Краткие правила для поддержания аккуратной и воспроизводимой структуры проекта.

## 1. Именование

- Ноутбуки: `NN_topic.ipynb` (пример: `01_baseline.ipynb`).
- Документы в `docs/`: `snake_case.md`.
- Файлы в `src/`: `snake_case.py` (или целевой формат стека в том же стиле).

## 2. Организация изменений

- Экспериментальные шаги сначала фиксируются в `notebooks/`.
- Стабильная логика переносится в `src/`.
- Любые изменения процесса отражаются в `docs/roadmap.md`.
- Для изменений, влияющих на результаты, обязательно обновлять `docs/results_summary.md`.

## 2.1 Research-процесс для экспериментальных PR

- Для каждого экспериментального запуска фиксируйте:
  - модель (`model1`/`model2`),
  - режим (`full`/`fast`/`smoke`),
  - ключевые параметры (`grid_steps`, `radius_list`, `max_batches`, `seed`).
- Если heavy-артефакты не коммитятся, в PR обязателен текстовый summary:
  - что запускалось,
  - какие метрики получены,
  - где лежат локальные артефакты.
- Любой вывод уровня "лучше/хуже" должен сопровождаться числом из CSV или ссылкой на таблицу в `docs/`.

## 3. Стиль коммитов

Рекомендуемый формат:
- `docs: обновить шаблон отчета`
- `chore: обновить структуру папок`
- `feat: добавить базовый скрипт подготовки данных` (когда начнется код)

Принципы:
- один коммит = одна цель;
- сообщение в повелительном/действительном стиле;
- без смешивания несвязанных изменений.

## 4. Чеклист перед PR/сдачей

- [ ] Обновлен `README.md` при изменении структуры/процесса.
- [ ] Актуализированы `docs/roadmap.md` и `docs/report_template.md` (если нужно).
- [ ] Обновлен `docs/results_summary.md` (если менялись результаты/метрики).
- [ ] Нет временных файлов и локальных артефактов в изменениях.
- [ ] Источники и требования согласованы с `docs/task_sources.md`.
- [ ] Изменения воспроизводимы другим участником без устных пояснений.
